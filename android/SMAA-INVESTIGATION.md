# SMAA investigation: Run 73 and the diagnostic fix

Baseline: `db2884ae940cdba19180f952274e35fd0ef30b7c`, Android Actions Run 73.
Reference: [iryoku/SMAA](https://github.com/iryoku/smaa/tree/71c806a838bdd7d517df19192a20f0c61b3ca29d).

## Findings and limits

The actual Run 73 generated pipeline **does perform SMAA on Mesa GLES**. A
controlled diagonal produced edges, nonzero weights, and 1,279 changed output
pixels. It is not valid to claim that the reference resolve is universally
bypassed or that a successful Android compilation proves it works on Adreno.
No RP5 runtime log or device execution was available for this investigation.
The persistent RP5 symptom is therefore **not yet assigned a proven root cause**.

Two integration defects were found:

* Lazy initialization uploads the lookup textures **before** saving the caller's
  texture bindings. The last upload leaves SearchTex bound to the game's active
  unit. Run 73's state test reproduces one changed binding on the first frame;
  subsequent normal frames pass. This can cause a transient first-activation
  visual change and desynchronize the renderer's texture cache. It does not,
  by itself, prove the reported sustained lack of AA. The state snapshot now
  precedes initialization and restores state on failure as well as success.
* Android used GLAD's desktop loader for an ES context. ES 3.0 sampler entry
  points are consequently null because desktop sampler objects start at 3.3.
  The renderer now chooses GLAD's ES loader from SDL's actual context profile.
  This enables the sampler-state isolation required by the post pass. This
  loader defect is also not asserted to be the sole cause of the reported image.

Reference shader compilation/FBO failures previously silently substituted SMAA
Lite while the menu still said Ultra. The build now exposes that fallback's
stage in the menu and records labeled shader errors and routing in the log.

## One frame, as generated by the workflow

`gfx_start_frame` takes the SDL drawable dimensions and assigns the game viewport
the same dimensions. The main scene is drawn directly into FBO 0 when MSAA is
off; with MSAA enabled, the game framebuffer is resolved into FBO 0 after the
display list and pending geometry have finished. `gfx_run` then calls the
renderer `end_frame`, which invokes `gfx_opengl_grade_frame` exactly once.

| Operation | Samples / reads | Writes |
| --- | --- | --- |
| Copy completed scene | FBO 0 / `GL_BACK` | `grade_fbo` / `grade_tex` |
| Grade, sharpen and other Post FX | `grade_tex`, unit 0 | `smaa_fbo[0]` / `smaa_tex[0]` |
| Reference luma edge detection | `smaa_tex[0]`, unit 0 | `smaa_fbo[1]` / `smaa_tex[1]` |
| Reference blending weights | edges on 0, AreaTex on 1, SearchTex on 2 | `smaa_fbo[2]` / `smaa_tex[2]` |
| Reference neighborhood resolve | color on 0, weights on 1 | FBO 0 / back buffer |
| Optional diagnostic view | color, weights, edges | FBO 0; only when explicitly selected |
| Screenshot / recorder hooks | finished back buffer | CPU/capture buffers |
| SDL swap | finished back buffer | display |

The SMAA result is **not** fed to a subsequent grade pass. Since Run 73, all
grading/sharpening precedes SMAA, so there is no later sharpening pass to undo
it. Screenshot and recording hooks do not replace the displayed image.
Color, edge, and weight targets are distinct. None samples its draw attachment.
Tests inspect the actual draw FBOs, sampler uniforms/bindings, viewport and
metrics during each production draw, rather than just checking source text.

All three targets use the drawable width and height; metrics are
`(1/width, 1/height, width, height)`. All SMAA inputs use linear/clamp sampling.
AreaTex is 160x560 RG8; SearchTex is 64x16 R8. The decoded lookup payloads are
hash-checked against the pinned upstream assets. Edge and weight targets are
cleared, including alpha. There are no sRGB conversions in the data passes;
the reference neighborhood blend operates in the existing gamma color space.

Ultra uses upstream `SMAA_PRESET_ULTRA`: threshold 0.05, 32 orthogonal search
steps, 16 diagonal steps, corner rounding 25. Multi maps to upstream High.
No thresholds or blend strengths were increased. The generated shaders now
call upstream's offset helpers as well as its pixel functions. ES precision is
explicit for floats, integers and sampler results.

`menuhandlerPostFxAA` writes `g_PostFxAA`, `postFxApply` copies it to
`gfx_post_aa`, and the config range is 0..4. The grade early-out explicitly
requires mode 0. No later assignment to reset mode 4 was found. The new runtime
log records setting changes and repeats the requested mode in delayed audits.

The post pass now isolates and restores programs, VAOs, texture units 0..2,
sampler bindings, active unit, separate read/draw FBOs, read buffers, viewport,
color masks, relevant enable bits and texture unpack/PBO state. Audits separately
preserve pixel pack/PBO state. The old initializer's binding leak has a failing
baseline regression and a passing fixed regression.

## Runtime diagnostics

`Post FX > SMAA View` contains Normal, Edges, Weights, Resolved and Difference x8.
Diagnostic selection is session-only; Post AA's existing values remain 0..4.
Normal is the ordinary final resolve. Weights displays all four channels, so
alpha-only weights are visible. Difference is the absolute resolve/input
difference amplified only for inspection; it does not change normal AA.

Two frames after selection/resize and again at frame 120, a bounded readback
compares the actual resolved back buffer with its pre-AA color input. The menu
shows E (edge pixels), W (weight pixels) and D (changed RGB pixels); the log adds
frame, dimensions, maximum change and GL error. These are live measurements,
not assumed shader success. Readbacks can cause a short hitch on those frames.
An empty or perfectly flat scene can legitimately have E/W/D equal to zero.

## Validation

`android/tests/verify-smaa.py` extracts and compiles the production post-processing
block **after every workflow patch**, then runs it on a real surfaceless GLES
3.0 context. CI must pass this test before building the APK. It tests:

* First use, repeated frames, Off/Ultra/High transitions and resizing.
* 1920x1080, 960x540 and odd target dimensions; several diagonal orientations.
* Lower error versus an independently calculated 8x8 edge-coverage reference.
* Zero changes outside the detected-edge neighborhood, unchanged flat fields,
  and unchanged exactly horizontal/vertical boundaries.
* Nonempty edge/weight passes and final changes; all diagnostic views.
* State restoration with inherited samplers, masks, stencil/scissor, PBOs and
  distinct read/draw bindings, including the audit frames.
* Exact pass order, four normal draws, no read/write feedback, texture units,
  linear/clamp filters and correct texel metrics; zero GL errors.
* SMAA still runs after sharpening; delayed audits at frames 2 and 120.

For the native-resolution shallow diagonal, the fixed pipeline changed 2,559
pixels, with zero changes outside the edge neighborhood. Mean square error
against the independent coverage reference fell from 3.4163 to 0.9516 (~72%).
These are controlled renderer results, not a claimed visual test on the RP5.

Each workflow uploads the generated renderer/menu, actual shader strings,
numeric results, source hashes and run/commit provenance. The APK's application
ID, committed signing key and run-number versioning are unchanged; CI verifies
the built APK signature and prints its identity and checksum.
